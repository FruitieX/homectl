# Reusable JavaScript

Implemented 2026-10-01. Definitions live in the database and configuration
exports. Older backups may omit the new fields. No runtime TOML settings are
needed.

## Choose the right building block

| Need | Use | Result |
| --- | --- | --- |
| Repeated ordinary operations | Visual action block | Native actions in the caller's plan |
| Custom reusable behavior | JavaScript action block or a script step inside a visual block | `{ actions, next_state? }` |
| Repeated condition | Visual or JavaScript condition block | Boolean or `api.unknown(reason)` |
| Shared calculation | JavaScript function block | Declared typed value |
| Sensor-derived state for native conditions/widgets | Computed helper | Boolean, enum, number or string |
| Time-based lighting | Computed source | Light profile; JavaScript can call shared functions |

Blocks live under **Settings → Blocks**. Choose Action, Condition or Function,
define named inputs and defaults, then choose Visual blocks or JavaScript.
Functions always use JavaScript and declare an output type. Action/condition
calls remain named blocks in routine flows, so callers need not read code.

## Typed inputs and shared functions

JavaScript blocks receive arguments as `inputs` and `ctx.inputs`. Arguments are
validated data, never replacements in JavaScript source. Device, group and
target arguments automatically declare their corresponding device dependencies
for the caller's captured context. Explicit dependencies can be added too.

A function receives `inputs`, `ctx` and `api`, returning its declared type.
Output types match block inputs, including JSON for structured values. Outputs
must be finite, serializable JSON within 64 KiB. Functions have no independent
subscriptions or state: they inherit the caller's frozen context.

For a function named `scale`, with Number inputs `value` and `factor` (default 2)
and Number output:

```javascript
return inputs.value * inputs.factor;
```

Select `scale` in the caller's **Shared functions** picker, then call:

```javascript
const level = api.functions.call("scale", { value: 0.2 });
return { actions: [api.actions.dim({
  targets: { groups: ["hall"] }, step: level,
})] };
```

Every script declares fixed function IDs. Each function declares its own
dependencies. Undeclared calls, missing definitions, wrong kinds, invalid
arguments/outputs and cycles fail visibly. Root scripts cannot call a transitive
dependency unless they select it explicitly. Limits: 16 direct dependencies,
32 resolved functions, 8 dependency/call levels. Invocations use fresh realms.

Functions do not grant callers additional access. Light-profile sources retain
only time/parameter context, without live device/helper values. All code runs
in supervised workers outside the state actor, without direct device, network
or database access.

## JavaScript action blocks

For Device input `light` and Boolean input `power`:

```javascript
return { actions: [api.actions.setPower({
  device: inputs.light, power: inputs.power,
})] };
```

Actions are validated and expanded through the ordinary native planner. Visual
blocks may mix ordinary actions and script steps; only selected branches run.
Every selected script must succeed before dispatch. Scripts cannot return
another script action. Newer manual intent can suppress delayed effects.
Returned actions use the invocation's captured devices, groups, helpers and
intent revisions, including actions generated by individual script steps.

`next_state` provides bounded per-call-site memory through the existing routine
coordinator. It is not shared global function state.

## JavaScript condition blocks

Return exactly `true`, `false`, or `api.unknown(...)`; truthy strings, numbers
and action objects are rejected. For an occupancy helper:

```javascript
const occupancy = api.values.get("occupied");
if (!occupancy) return api.unknown("Occupancy is unavailable");
return occupancy.value === true;
```

Use these blocks in **Only if** and **Choose**. Script results and native branch
decisions use a coherent captured device/group/helper frame. Errors and unknown
values are visible in status/history and do not authorize that condition.
Conditions cannot dispatch actions or save memory.

JavaScript predicates in transition/held-for triggers are rejected at compile
time. Use a computed helper as the script-derived input to a native transition
or held-for predicate instead.

## Computed helpers

Under **Settings → Helpers**, choose **Computed value**, set the helper type,
declare device/group and helper dependencies, select shared functions, and set
refresh cadence (1 second–1 day). Return a value matching the helper type:

```javascript
const mode = api.values.get("house_mode");
if (!mode) throw new Error("House mode is unavailable");
return mode.value === "home";
```

Only selected helper dependencies appear in `api.values.get`. Device/group
context follows ordinary script declarations. Missing dependencies and cycles
are rejected. The initial value is the startup fallback while the first result
is pending; it is not a known computed result.

Inputs changing cause recomputation; the server also refreshes at the configured
cadence with no browser open. Value changes drive native helper predicates and
history. Durable values survive restarts; session values do not.

| Status | Display and condition behavior |
| --- | --- |
| Pending | No successful result for this definition; unknown to conditions |
| Fresh | Successful value is available |
| Updating | Previous successful value stays available while inputs recalculate |
| Stale | Last-good value stays displayed with an error; unknown to conditions/scripts |
| Disabled | Last value stays displayed; unknown to conditions/scripts |

Failures retain the last-good value and successful-evaluation timestamp.
Obsolete results are rejected when inputs, definitions or owner generations
change. Definition edits reset freshness until recalculated. Computed helpers
are read-only in controls, API and routines. Switch to Manual value to make a
helper writable.

## Preview, usages and edits

**Preview draft** accepts an unsaved block plus test inputs or a computed helper.
It captures current values, runs workers outside the actor, and returns values,
condition diagnostics or selected action steps. It never saves the draft,
dispatches actions or changes helper values. Editing marks an earlier preview
out of date. Custom source previews execute actual JavaScript and its functions.

Editors link related routines, blocks, computed helpers and sources. Shared
function pickers also link directly to definitions. Edits validate enabled
callers, advance affected routine/helper/source revisions and invalidate older
work. Block and caller revisions persist in one transaction. In-use blocks
cannot be deleted; optimistic concurrency preserves conflicting drafts.

API:

- `GET /api/v1/config/blocks` and `PUT/DELETE /api/v1/config/blocks/{id}`
- `POST /api/v1/config/reuse-preview` with `{kind:"block", block, inputs}` or
  `{kind:"helper", helper}`
- Existing helper/source APIs include optional computation/function fields.

See [blocks](automation-blocks.md), [script actions](routine-scripts.md), and
[implementation and verification](javascript-reuse-implementation.md).

## Configuration assistant

The built-in assistant can search/attach Action, Condition and Function blocks,
reuse their typed signatures, and propose creating, updating or deleting them.
The shared authoring reference covers visual calls, JavaScript steps, fixed
function imports, strict condition results, computed helpers, light-profile
sources, scene selection, rollout and timers. The routine-only draft endpoint
uses the same reference but cannot create dependent entities; ask in the main
assistant panel for a plan that creates a block/helper alongside its routine.

Context includes existing reusable definitions, helper computation/read-only
status and current helper freshness, device sensor values, room/scene IDs and
the configured schedule timezone. Block source bodies are included within a
bounded catalog budget; attach a block to supply its full definition when its
body is omitted from the summary.

Plans validate dependency order, typed calls, function/helper graphs, existing
enabled callers and source imports before review. Only selected operations are
applied. Missing or rejected dependencies make a caller fail visibly rather
than implicitly creating unaccepted entities. Each application revalidates
against the latest state. Shared block changes use the editor's mutation and
transactional persistence path; edits advance affected callers' revisions.
A block changed after review requires a new plan instead of overwriting that
edit. In-use blocks cannot be deleted until their callers are removed.

Generated JavaScript remains a proposal: schema/syntax validation cannot prove
its behavior. Review the source and use **Preview draft** or stored scenarios
before enabling an automation. Creating a proposal and previewing its scripts
never dispatch device commands.

The assistant integration tests exercise a combined function/block/helper/source/
routine plan, script-worker previews, shared-edit revision propagation, selective
acceptance, stale review protection and database restoration. Executable prompt
examples and schema-variant coverage checks help keep the reference current.
These tests also caught a Boa syntax-parser stack overflow on ordinary nested
scripts; the server runtime now reserves an 8 MiB thread stack to match the test
and main-thread stack size. Script execution remains in supervised workers.
