# Settings UX completion plan, v2

This is the next implementation handoff after [the original redesign plan](docs/settings-ux-redesign-plan.md). It is based on the 18 mobile screenshots in `refactor-wip/` dated 2026-09-24 17:08:14 and an inspection of the current UI code. The first plan's checked boxes are an inventory of work attempted, not proof that the experience is finished. The goal here is a calm configuration UI that tells a beginner what is saved, what is happening now, why, and how to change it, while keeping advanced controls reachable.

Work in the order below. Correctness and interaction mode come before spacing and colors. Do not mark a task complete because the component renders; verify the behavior and the review states listed at the end. Preserve existing API mutations and the database as the canonical user-config store.

## 1. Fix the shared read/edit contract first

**Current defect:** `ui/ui/config/Section.tsx` calls `api.begin()` as soon as an editable section opens. Its `readView` is therefore never shown for normal editable sections. This is why screenshots 1–3 and 6–14 show Save, Remove, and nested Edit controls immediately upon expansion. It contradicts the product decision in the original plan.

- [x] Remove the open-implies-edit effect from `Section`. An opened section initially renders `readView` even when `editable` is true. Put one clearly labeled **Change** action in the expanded read body or heading actions, outside the disclosure trigger. Pressing it calls `api.begin()` and replaces that section's read content with `renderEditor`.
- [x] Only the section being edited shows Save and Cancel. Do not render a disabled Save plus “No changes yet” merely because the user expanded a section. Cancel exits edit mode even if nothing changed; a dirty Cancel/disclosure/page navigation uses the existing discard guard. Save returns to the updated read view without closing the section. Errors keep the editor and draft open. Restore focus to Change after Save/Cancel and announce the result.
- [x] Allow at most one section editor on a detail page at a time. Opening another read section is fine; starting another edit while a draft is dirty must offer Save, Discard, or Stay. Keep the existing conflict detection and merge-only-owned-fields behavior in `useSectionEditor`.
- [x] A `?section=` deep link expands and focuses the **read view**, not an editor. `?target=` scrolls to and highlights the relevant item; it must not silently start editing. A repair link may label its destination “Change this target,” but the destination must still make the edit transition explicit.
- [x] In a collection section, use **one** Change action for the section. In read mode, rows open explanations or direct links. In edit mode, Add/Remove/Move appear and tapping a row opens **one** inline row editor. Do not put an Edit button on every row. Hide reorder controls for a single row and avoid separate selector-plus-Add pairs when one “Add…” chooser can do the job.
- [x] Keep immediate device controls and helper “Set current value” actions directly actionable, with progress and result feedback. Those are commands, not persistent section edits.

The intended states are:

| State | Visible content | Actions |
| --- | --- | --- |
| Collapsed | Title, one useful summary, actionable issue badge if needed | Expand |
| Expanded read | Saved values in plain language, current evidence clearly labeled | Change; relevant direct links/commands |
| Editing | Inputs for this section; one child editor at a time for lists | Save, Cancel; Add/Remove/Move where relevant |
| Save failure/conflict | Draft remains visible with a specific correction | Retry or resolve conflict |

This pattern answers the concern about too many Edit buttons. One Change action per meaningful section is justified because it separates reading from persistent change. A global page-wide Edit mode would expose too many controls at once.

## 2. Repair data and status truth before visual polish

### Scene color editor: production format mismatch

- [x] Fix `ui/ui/SceneColorEditor.tsx`. It detects and emits tagged colors (`{Hs: ...}`, `{Rgb: ...}`), but `server/src/types/color.rs::DeviceColor` uses untagged serde and `ui/bindings/DeviceColor.ts` is a union of plain `{h,s}`, `{r,g,b}`, `{x,y}`, and `{ct}`. A saved purple HS target currently appears as **No color** with a gray preview in screenshot 7, while the scene result above has a purple swatch. Do not patch this by changing fixture data to an invalid tagged shape.
- [x] Use one typed color parser/formatter for `SceneColorEditor`, `SceneResolvedColorPreview`, and the final-effect preview. Recognize all four real variants. The editor must preserve an existing XY value even if a simplified color picker cannot edit XY directly; offer an advanced XY editor or a deliberate conversion, never silently clear it. Mode changes emit valid untagged data.
- [x] The final-effect swatch is visual shorthand alongside On/Off and brightness. Give it an accessible color name and exact-value detail; do not make color the only carrier of meaning. A target that sets no color has no swatch. If power is Off, represent Off clearly and avoid implying the light is physically showing that color.
- [x] Add focused tests for loading, changing, saving, and reloading HS, RGB, XY, and CT scene targets. The editor, target read row, and final-effect swatch must agree, including the existing Movie fixture in screenshots 6–7.

### Routine live versus draft status

- [x] In `ui/app/config/routines/detail.tsx`, `previewIsDraft = draftDefinition !== definition` becomes true as soon as an untouched section opens because a draft object was copied. Base it on actual edited fields/dirty state. Opening When must not hide saved live trigger status or label an unchanged definition as a draft.
- [x] Fix `triggerStateSentence` in `ui/ui/routine-runtime.tsx`: if the routine is enabled but a trigger status is absent, do not say “enable the routine.” Say what evidence is absent, such as “No trigger evaluation received yet; waiting for a report from Living room motion.” Add a test for this exact enabled/unknown combination.
- [x] Keep three facts separate: the saved requirement, its **current** evaluation, and a **recorded past** attempt/run. Do not infer why a past run did not happen from today's condition. In screenshot 11, prefer a compact header such as “Enabled · waiting for motion. Current condition unmet: motion is inactive,” followed by a timestamped last event or “No matching event in retained history.” Put the stored requirement in Only if. Drop the redundant “Routine” badge and vague “Its last recorded run ran the actions below.”
- [x] Rework `ui/lib/routineNarrative.ts` so current readings do not rewrite the saved condition. “Only if motion is active and cooldown is off” remains the requirement whether motion is currently active or inactive. Show “Not met now: motion is inactive” separately. Update tests that currently lock in long “Not running: only if…” sentences.
- [x] Fix `ui/lib/routinePolicy.ts` and its tests. The server rejects an over-`max_actions` plan **as a whole** (`server/src/core/event.rs::dispatch_v2_plan`); the current UI says excess actions are dropped. The collapsed Advanced summary and Max actions help must both state the same server behavior.

### Scene preview and recorded evidence

- [ ] If a scene has a script, label the list “Saved target effects before script” or equivalent. Do not promise these are the final effects when the script can override them. Keep the one-row-per-final-device list and a short link to target precedence/technical details. Surface unresolved targets with a repair link beside the warning, before Activate.
- [ ] Align every header count, preview count, and warning with the same resolved-effect model. Distinguish a missing direct target from a missing device inside a room. If Activate skips references, state exactly how many and which available devices still receive commands. API acceptance must not be described as physical delivery.

## 3. Finish the promised navigation model

- [x] Replace the full-screen overlays still used by connections (`ui/app/config/integrations/page.tsx`), helpers (`ui/app/config/helpers/page.tsx`), and computed sources (`ui/app/config/sources/page.tsx`) with true detail-page components at their existing `/:id` routes. The current connection in screenshot 15 is still an overlay with Settings/Advanced JSON tabs. Keep confirmation dialogs small; use the page for reading status, changing configuration, and browser Back.
- [x] Put connection status and one next action at the top. “Enabled” means configured to run; it does not prove the bridge is connected. Show a linked device-report issue with last-heard time when known. Put required fields under Primary settings, optional schema groups below, and JSON in a closed advanced section. Preserve masked secrets and unknown keys. Put Delete last, outside the JSON editing form.
- [x] Helper detail should lead with current value and whether it survives restart. Make “Set current value” an immediate action; place initial value, type rules, and enum-option editing in readable sections. Computed-source detail should lead with output, freshness, and a Preview that says whether it evaluates saved or draft values. Keep script/raw controls closed until requested.
- [x] On phones, remove repeated location signals: the app bar currently says “Settings · Rooms,” then detail pages show Back, `Settings / Rooms / Hallway`, and the title. Use one mobile pattern across lists and details. Recommended: app bar “Settings”; list page has its own title; detail page has Back + item title/status, with breadcrumbs only at wider widths. Maintain stable URLs and a visible Back after direct load.

## 4. Page-by-page UX pass

### Rooms — screenshots 1–3

- [ ] Header says “1 available device, 1 missing reference” where appropriate; omit “0 linked rooms” and “used by 0 scenes.” Explain use by the one routine without a chain of counts. A missing saved member must show its full key on expansion, with Copy, Replace, and Remove in edit mode. Do not truncate the only information needed for repair.
- [ ] Remove the inner “Members” card inside the Devices section. Read mode shows compact member rows; edit mode shows selected rows and a search field. Remove a row's bare × in favor of a labeled action accessible to keyboard and screen readers.
- [ ] For Linked rooms, use one line in the empty state: “No linked rooms. Search to add one.” Show the ordering explanation only when there are two or more links and order changes the result. A search result that would create a cycle must be disabled with a plain reason.
- [ ] In Details, use a compact Name field and Hidden row. Align the Hidden control with its label, use one sentence of help (“Hide from main controls; automations still use it”), and shorten the permanent-ID text to “ID: hallway · used by 1 routine.”

### Devices — screenshots 4–5

- [ ] Hide sensor-specific placeholder text on non-sensors. In Display and sensor behavior, keep the custom label and relevant controls; move raw device keys to Technical details. Use consistent sentence-case actions (“Use integration label,” “Save”).
- [ ] Put Technical details before the final danger section. In the danger section, separate Replace references from Delete, explain consequences in one sentence each, and let the existing confirmation carry the detailed impact list. Keep the replacement picker searchable for a 300-device setup.
- [ ] On a narrow phone, replace the floating Filters popover that covers the result with an anchored full-width disclosure or sheet. Search should have room to type; put Filters and bulk Select in a secondary row or menu. Show active filter chips and one Clear filters control. After applying filters, return focus to the result count/list and leave the result unobscured.

### Scenes — screenshots 6–10

- [ ] Read mode for Device targets and Room targets shows human target rows with resolved effects. A single **Change targets** action enters collection editing; only then show Add, Remove, Move, and the inline editor for the selected row. Do not show “Edit target” on every row, red × marks, or disabled Save in read mode.
- [ ] Remove repeated headings such as “Device targets” inside the Device targets section. Show room override/order help only when multiple room targets can overlap. Hide up/down controls if only one room target exists.
- [ ] In target editing, make the effect preview stay visible when a row changes. Use clear modes such as “Set a state,” “Follow a device,” and “Use another scene.” For a state target, show Power, Brightness, Color, and Fade only when applicable. Provide a numeric way to set an exact brightness beside the slider. The existing Color Mode editor must first pass the real-format tests above.
- [ ] In Advanced script, show a short saved-script preview and “Change script.” A one-line script should not open a large empty code pane. Resize the editor to useful content with an upper bound, and keep Save/Cancel within the editing section.
- [ ] In Details, condense the immutable ID explanation and Hidden help. Keep Activate visually distinct from editing. If references are missing, offer “Review 2 skipped references” adjacent to the activation preview.

### Routines — screenshots 11–14

- [ ] Open When, Only if, and Then into readable content, not builders. When shows each trigger as “Living room motion becomes active” plus its current evidence; Only if shows the saved requirement and current result; Then shows “Activate Normal” and any ordered actions. Each section has one Change action.
- [ ] When editing triggers, hide raw node IDs like `t1` unless Technical details is opened. If there is no matching live trigger status, use the corrected unknown-state copy above. Keep only one trigger editor expanded.
- [ ] When editing conditions, replace `/value truthy` and `helper entryway_cooldown eq false` with field labels and human comparisons. The device/field/value picker must offer autocomplete and current/recent values as promised in the first plan. Keep JSON pointers under an Advanced custom-path control. Replace the condition-type select plus Add button with one “Add condition…” chooser. Show one nested clause editor at a time.
- [ ] When editing Then, call the section **Actions**, not Program/Native steps in the beginner view. Show each step as a sentence. Click a step row to edit it; show Move/Duplicate/Remove in edit mode, not on every default row. Program type and execution policy belong under Advanced.
- [ ] The what-if trigger selector must use its actual phrase, not “state change.” Say whether it evaluates saved or unsaved values. Place the first decisive reason before detailed traces. Advanced opens to a concise read summary; its technical policy form appears only after Change.

### App, floorplan, and list/empty states — screenshots 16–18

- [ ] Appearance can retain the current clear theme and named color choices. Shorten blur and density descriptions; keep compact mode's touch targets accessible. Reduce nested outlines where one section boundary is enough.
- [ ] Floorplan still shows a contextual sentence, “How drawing works,” and an always-visible “How to Use” list. Remove the permanent list (`ui/app/config/floorplan/page.tsx`) and keep only one contextual instruction for the active tool, with optional Help. Put background image in Display/Layout settings. Ensure Walls mode does not present Device painting controls as part of its active toolbar.
- [ ] On Helpers empty search, remove the duplicate Clear near “0 of 1 shown” if the empty state already has Clear search. Use one empty-state action and one short sentence. Apply this consistency rule to other filtered lists.

## 5. Visual and copy system pass

- [ ] Establish one mobile spacing/typography rhythm for all settings pages: page title, status sentence, section heading, row label, helper text. Secondary facts must remain readable; reserve the smallest type for technical IDs and timestamps. Use one button height and consistent Save/Cancel placement. Avoid nested rounded cards unless the inner content is a real selectable object.
- [ ] Align form labels, controls, and helper text on the same grid. In particular, fix the floating Hidden checkbox in room Details, the crowded routine trigger/step action rows, and the filter overlay edge alignment. Let long names wrap before shrinking action targets.
- [ ] Remove copy that repeats the heading or instructs the obvious. Examples: “Devices from linked rooms become part of this room” twice; “No changes yet” under a section just opened; a large How to Use panel after floorplan contextual help. Keep a sentence only if it changes a decision or explains a consequence.
- [ ] Keep warning color for a concrete repair. Ordinary false conditions, a disabled routine, and an empty room are neutral. A warning must name what is affected and link directly to a correction. Use “requested,” “reported,” “saved,” and “predicted” consistently; never imply physical delivery from an accepted command.

## 6. Verification gates: do not declare done before these pass

- [ ] Run a scripted read/edit check on one room, routine, scene, helper, source, and connection: expand without editing; enter Change; alter one field; Save; reopen; Cancel; invalid input; server failure; server-side conflict; dirty browser Back. Confirm no unrelated fields or live state are overwritten.
- [ ] At 430px phone width, 200% zoom, and desktop width, inspect each of the 18 screenshot states again in light and dark mode. Check keyboard focus, software-keyboard picker behavior, bottom-nav clearance, button alignment, long names, reduced motion, and screen-reader names for color swatches and icon actions.
- [ ] Test HS/RGB/XY/CT scene color round-trips, a scripted scene's cautious preview label, an unresolved direct target plus missing room member, and a scene activation with skipped references. Confirm the exact same count appears in header and preview.
- [ ] Test an enabled routine with current condition false, true, and unknown; an absent trigger status; an untouched expanded section; a dirty draft preview; blocked history after restart; and an over-`max_actions` run. Compare every UI sentence against server behavior.
- [ ] Test a 300-device catalog with duplicate names, missing saved references, search by name/room/integration/ID, selected items surviving picker filters, and bounded initial rendering. Confirm no long native dropdown or unfiltered checkbox wall returns.
- [ ] Ask a reviewer unfamiliar with the implementation to: find why motion did not turn on lights; change a threshold using current/recent values; repair the missing Hallway device; repair a scene reference; rename a device; find a device that stopped reporting; create a scene; create a routine. Record where they hesitate and fix the UI, not the reviewer.
- [ ] Run the relevant UI checks (`pnpm tsc`, `pnpm lint`, `pnpm test`, `pnpm build`) and relevant Rust tests for changed behavior. Review screenshots after the final code change. Update the original plan's checkboxes only when the corresponding behavior is verified. Make conventional commits and push only the intended implementation files.

**Definition of done:** A beginner can open an item and understand its saved state and current evidence before seeing a form; can choose Change once for the part they found; can complete common repairs without raw IDs, JSON pointers, or external MQTT tools; and never receives a confident statement that the runtime evidence cannot support.
